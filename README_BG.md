# BAGER SITE LINK v1.0 — пилотен пакет

## Какво е изградено
- PWA-подобен уеб интерфейс, отварян с линк; не се изисква инсталация от Google Play.
- Роли: диспечер, шофьор, оператор, ръководител обект, клиентски преглед.
- Еднократни покани с криптографски случаен токен, хеширан в базата, срок 24 часа и еднократна употреба.
- Начало/край на смяна.
- GPS запис с точност, скорост, посока, време на устройството и време на сървъра; дедупликация чрез device_event_id.
- Локална опашка за GPS при кратка загуба на интернет и синхронизация при възстановяване на връзката.
- Курсове с контролиран жизнен цикъл: опашка → товарене → натоварен → път към депо → депо → разтоварен → връщане → завършен.
- Товарен билет за всеки курс, отчетен обем и отделен статус за потвърждение.
- Диспечерски екран с количества, активни/завършени курсове, камиони, GPS карта и последни събития.
- Пилотни демо данни: един багер, два камиона и диспечер; шофьорите, операторът и ръководителят се създават с персонални покани и се свързват с конкретна машина.

## Как да стартираш на Windows
1. Инсталирай Python 3.12.
2. Разархивирай пакета в папка, например `C:\BAGER_SITE_LINK_v1`.
3. Отвори папката и стартирай `run_windows.bat`.
4. Въведи дълга уникална администраторска парола, когато бъде поискана.
5. Отвори `http://127.0.0.1:8000` на компютъра.
6. За телефон в същата Wi-Fi мрежа отвори `http://IP-НА-КОМПЮТЪРА:8000`. Разреши GPS.

## Демо поток
1. Диспечерът влиза с администраторската парола.
2. Създава покани за двама шофьори и оператор. При покана за шофьор избира камион.
3. Изпраща всеки индивидуален линк през Viber.
4. Шофьорът отваря линка, започва смяна и разрешава GPS.
5. Диспечерът създава курс. Системата назначава свободния камион и неговия шофьор.
6. Шофьорът маркира етапите в момента на настъпване.
7. Операторът записва действителния обем на натоварения курс.
8. Диспечерът вижда потвърдените количества и хронологията.

## Важни технически ограничения
- GPS в браузър изисква HTTPS, освен на localhost. Отваряне по локален IP в телефон често няма да даде GPS разрешение. За реален пилот публикувай зад HTTPS домейн.
- Браузърната геолокация не гарантира проследяване при заключен телефон, затворена страница или агресивно спиране на браузъра от Android. За надеждно фоново проследяване е необходим отделен Android клиент/foreground service.
- GPS се записва само след изрично разрешение и активна смяна. Спирането на смяната прекратява приемането на GPS точки.
- GPS позицията не доказва кубатура. Кубатурата в тази версия се въвежда в товарния билет от оператор/диспечер; трябва да се уточни методът и дали е потвърдена.
- Картата използва OpenStreetMap плочки и Leaflet от CDN; изисква интернет. Не е интегрирана камера/WebRTC във v1.0.
- SQLite е локална пилотна база. За многопотребителски реален обект използвай PostgreSQL през `DATABASE_URL` и изпълни `sql/004_site_link_runtime.sql` след Central Data Core миграциите.
- Приложението не е публикувано, не е penetration-tested и не е готово за реални лични данни без HTTPS, резервни копия, тестове на правата, GDPR преглед и мониторинг.

## PostgreSQL
Пример:
`DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DBNAME?sslmode=require`
Изпълни Central Data Core миграции 001–003, след това 004. Стартирай приложението с отделен DB потребител с минимални права. Не използвай Supabase service_role ключ в браузъра.

## Данни и архив
- SQLite: файл `bager_site_link.db` в работната папка. Спирай приложението преди ръчно копиране.
- PostgreSQL: ежедневен backup и отделно криптирано копие; ежемесечен тест за възстановяване.
- GPS: пилотният пакет пази точките в оперативната база; задайте конкретен срок за задържане и процедура за изтриване/анонимизиране след правен преглед.
- Видео: не е включено във v1.0.

## Интеграция с Central Data Core
В PostgreSQL `sql/004_site_link_runtime.sql` създава runtime таблици с отделни `core_organization_id`, `core_project_id` и `core_asset_id` връзки. След като съпоставите пилотната организация/обект/машини с вече съществуващите Core записи, GPS точките и оперативните събития се отразяват и в `gps_points` / `operational_events` чрез тригери. Runtime журналът остава подробният източник за SITE LINK. Не пускайте тази миграция в продукция без staging тест и проверка на правата на DB ролята.


## Ръчно свързване към вече съществуващ Central Data Core (PostgreSQL)
След първото стартиране на приложението в PostgreSQL, намери runtime записите:
```sql
select id, name, core_organization_id from public.site_link_organizations;
select id, code, name, core_project_id from public.site_link_projects;
select id, code, core_asset_id from public.site_link_assets;
```
След това попълни съответствията с реалните UUID от Central Data Core:
```sql
update public.site_link_organizations set core_organization_id = '<CORE_ORGANIZATION_UUID>' where id = '<SITE_LINK_ORGANIZATION_UUID>'::uuid;
update public.site_link_projects set core_project_id = '<CORE_PROJECT_UUID>' where id = '<SITE_LINK_PROJECT_UUID>'::uuid;
update public.site_link_assets set core_asset_id = '<CORE_ASSET_UUID>' where id = '<SITE_LINK_ASSET_UUID>'::uuid;
```
Повтори за багера и двата камиона. След това GPS, събитията, курсовете, товарните билети и количествата се отразяват и в съответните канонични таблици на Core Data Core чрез тригери. Ако съответствията не са попълнени, runtime данните пак се записват в `site_link_*`, но не се копират в Core таблиците.

## Какво не е включено в v1.0
- Камера на живо / WebRTC / видеоархив.
- Надеждно фоново GPS проследяване при заключен телефон или затворен браузър.
- Автоматично разпознаване на разтоварване само по геозона.
- Счетоводни фактури и плащания; финансовите записи остават в Central Data Core.
- Автоматична политика за изтриване/анонимизиране на GPS и медия; тя трябва да се определи преди реално събиране на лични данни.
- Вградено ограничаване на опитите за вход; при публично внедряване добави rate limiting/WAF на reverse proxy.
- Автоматична офлайн опашка за всички действия; само GPS точките се пазят локално и се синхронизират. Курсовете и товарните билети изискват връзка.
